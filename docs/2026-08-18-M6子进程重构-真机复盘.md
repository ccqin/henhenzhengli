# M6 子进程架构重构 — 真机实施复盘

> 2026-08-14 ~ 2026-08-18 · DesktopManager · 壁纸 + 图标层子进程化
>
> 一句话结论：M6 的子进程架构全部落地；计划中的 WorkerW 挂载方案在本机被证伪，
> 最终采用 **Owner = SHELLDLL_DefView** 技巧（Stardock Fences / Layouter 同款）实现 Win+D 免疫。

---

## 1. 最终架构

```
DesktopManager.App（主进程）
 ├─ 托盘 / 设置窗口 / 配置 / 桌面文件监听 / 播放治理（全屏、锁屏、电池暂停）
 ├─ 每屏启动 1 个 DesktopManager.Player.Wallpaper.exe（壁纸渲染）
 ├─ 每屏启动 1 个 DesktopManager.Player.Icons.exe（图标层渲染 + 交互）
 └─ stdin/stdout JSON 行协议（IpcChannel）：Ready{hwnd} 上报、指令下发、事件上报
```

**窗口形态（终态）**：子进程窗口 = 普通顶层窗口 + `WS_EX_TOOLWINDOW | WS_EX_NOACTIVATE`
（壁纸另加 `WS_EX_TRANSPARENT` 点击穿透），关键一步：

```csharp
SetWindowLongPtr(hwnd, GWL_HWNDPARENT, hShellDefView);  // Owner = SHELLDLL_DefView
```

由此获得三个特性：
1. **Win+D / 显示桌面免疫**——owned 窗口跟随 owner，owner 是 shell 自己的窗口，从不被"显示桌面"最小化；
2. **Z 序天然贴桌面层**——永远在普通窗口之下、桌面图标层附近；
3. **无跨进程渲染问题**——owner 是顶层窗口间的关系，不是 SetParent 父子挂载。

Z 序编排（图标层在壁纸之上）仍由主进程 `BottomPair` 完成，`Z 看门狗`（2s 条件检测浮高）保留兜底。

## 2. 三条技术路线的真机结论

| 路线 | 原理 | 本机结果 |
|---|---|---|
| **A. SetParent 进桌面层**（WorkerW / Progman，Lively 计划方案） | 窗口成为桌面子窗口，天然免疫 Win+D | ❌ **物理输出失效**：窗口 vis=True、坐标对、PrintWindow/BitBlt/PrtSc 全能看到内容（DWM 合成缓冲里有），但**显示器不显示**（人眼验证）。换 WorkerW/Progman、硬/软渲染、PMv2 DPI、显示时序、色键透明全试过，无用。属显卡驱动（Intel A780 核显）对跨进程桌面层子窗口的非标行为 |
| **B. 顶层窗口 + 置底**（M5 路线） | 普通顶层窗口 SendToBottom | ⚠️ 显示正常，但 **Win+D 被最小化**；靠 WH_KEYBOARD_LL 键盘钩子吞 Win+D 或事后恢复（体验差） |
| **C. 顶层 + Owner=DefView**（Fences/Layouter 路线）✅ | owned 窗口跟随 shell 的桌面图标视图 | ✅ 显示正常 + **真实键盘 Win+D 实测免疫**，钩子/恢复逻辑全部不需要 |

补充实验记录（路线 B 的排障过程，全部为真机实测）：
- 补 `WS_MINIMIZEBOX/MAXIMIZEBOX/THICKFRAME`（对齐 Layouter 样式）→ 无效，仍被最小化；
- 去 `WS_EX_NOACTIVATE` → 无效；
- 提升到 HWND_TOP（排除贴底 Z 序因素）→ 无效；
- **对照实验**是定位关键：同屏同时运行 Layouter（活）与我们（死），逐样式位 diff 后锁定 Owner 差异。

## 4. 方法论教训（重要）

1. **BitBlt / PrtSc / PrintWindow 截图链不能证明"用户看得见"**。
   它们读的是 DWM 合成缓冲，与物理显示输出是两条链路（本机 MPO/驱动行为下可以分叉）。
   涉及"是否真的显示"的验收，只有**人眼**或显示器输出链取证可信。
   本次为此反复横跳了多轮（"截图有画面"vs"用户说黑屏"），教训深刻。
2. **对照实验 > 猜测**。Layouter 同屏对照 + 逐样式位 diff，一次锁定 Owner 差异；
   此前对单一窗口的样式位实验（加 MINIMIZEBOX、去 NOACTIVATE、提顶）全部无效但各自只能排除一个因素。
3. **历史"真机验证"可能是像素检测**。8-14 上午 2110f61 的 Progman 方案"验证通过"实际是被截图链欺骗，
   当天下午用户即报告黑屏——读旧提交的验证结论时要看验证手段。
4. **会话跨天时先对时间戳**。本次曾把三天前（08-14）的旧日志当当天现场分析，浪费多轮。
   日志分析前先 `Get-Date` 对齐。
